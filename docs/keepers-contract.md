# Keepers: contract design (Checkpoint A)

Status: **design for review**. No code yet.
Target: NEAR Hackathon, Track 10 "NFTs That Do Something".
Contract crate: `contracts/keepers` (Rust, near-sdk `=5.30.0`, near-contract-standards `=5.30.0`, matching the existing workspace).

## 1. What the NFT does

A **Keeper** is a collectible vault creature. Each token is a small account that lives inside the contract:

| Behavior | How it works on chain |
|---|---|
| **Holds funds** | Each token has its own NEAR balance, tracked by the contract (`Card.balance`). Anyone can top it up. Only the current owner can withdraw. |
| **Earns its own royalties** | Every secondary sale through the built-in market credits **10%** of the price to the *token's* balance, not to the creator. The creator only receives the mint price. |
| **Evolves** | The tier (matte → brushed → holographic → animated) is a pure function of the token's on-chain balance. Views return it and the on-chain SVG art changes with it. |
| **Grants access** | `is_holder(account_id)` is the credential. The `/vault` page opens only for an account that proves it controls a holder wallet. |

The balance belongs to the token, not to whoever owned it before, so selling the NFT moves the money, the tier and the access together.

## 2. Key decisions

### 2.1 A new contract, not a retrofit of Everkeep
The existing `collection` and `wallet` contracts tie each NFT to a sub-account holding demoUSD and require an ML-DSA signature for every transfer, so no standard marketplace can move them. Keepers is a separate, small contract (~600 lines target) that judges can read in one sitting. The Everkeep contracts stay deployed and untouched.

### 2.2 Funds are held by the contract, per token (not sub-accounts)
- **Pros:** one contract, atomic accounting, no cross-contract calls to read a balance, and a simple solvency invariant (§6).
- **Cons:** the token is not a "real" NEAR account. That's acceptable: the Phase 2 brief asks for a balance "held by the contract for that token".

### 2.3 Tier metric: balance thresholds
I compared the three candidates:

| Metric | Gameable? | Visible in a 2-min demo? | Ties to the other features? |
|---|---|---|---|
| **Balance (chosen)** | Only by locking real NEAR in the card, which then really holds that value | Yes: one resale or one deposit moves it | Yes: royalties and deposits raise it, withdrawals lower it |
| Number of trades | Free wash trading between two accounts you own (the royalty you pay comes back to your own card) | Yes | Weakly |
| Holding duration | No | No: you'd need days, or thresholds measured in seconds | No |

The tier is therefore an honest signal of "how much this card holds". It goes down when the owner withdraws, which makes withdrawing a visible trade-off.

| Tier | Frame | Balance threshold |
|---|---|---|
| 0 | `matte` | < 0.5 NEAR |
| 1 | `brushed` | ≥ 0.5 NEAR |
| 2 | `holographic` | ≥ 2 NEAR |
| 3 | `animated` | ≥ 10 NEAR |

Thresholds are compile-time constants, set low so the demo works with testnet faucet amounts. The front end's existing `CardFrame` frames (`matte`, `metal`, `holo`, `animated`) map 1:1 onto these tiers.

### 2.4 Royalties: enforced only by the built-in market
**Built-in market (enforced).** NEAR has no way to attribute a plain NEAR transfer to a token, so a royalty paid to the contract by an external marketplace (NEP-199 payout) could not be credited to the right card. The contract therefore runs its own fixed-price market (`list`, `delist`, `buy`). There the split is atomic: `royalty = price × 1000 / 10000` goes to the card, and the rest goes to the seller.

**External transfers (not enforced).** NEP-178 approvals still work, so any wallet or marketplace can *transfer* a Keeper. A sale settled off-contract bypasses the royalty, as with every NEAR NFT. This is documented as a known limit.

### 2.5 Character and art
The frog art is dropped from this collection. The Keepers are an original, crypto-native PFP character:
- a round **vault-bot creature** with a keyhole visor;
- shown as a bust portrait with bold flat colors.

**Traits from on-chain DNA.** Each Keeper gets a `dna: u32` at mint (from `env::random_seed()`). The DNA picks 4 trait layers: background, shell color, visor and accessory.

**Art is generated by the contract.** `nft_token` returns `metadata.media` as an inline `data:image/svg+xml` image built from DNA + tier, so any wallet shows the current tier and nothing is hosted off chain. The front end draws a richer version from the same DNA inside the existing `CardFrame`.

**Limit:** validators can bias `random_seed`. Since traits are only cosmetic, this is acceptable.

### 2.6 Wallet
Keep `@hot-labs/near-connect`. It already works with Intear in this repo, and switching to the wallet selector adds risk without adding features.

## 3. State

```rust
#[near(contract_state)]
pub struct Contract {
    tokens: NonFungibleToken,             // near-contract-standards: owner_by_id, metadata, enumeration, approvals
    metadata: LazyOption<NFTContractMetadata>,
    creator: AccountId,                   // receives the mint price, nothing else
    cards: LookupMap<TokenId, Card>,
    next_id: u64,                         // token ids are "1", "2", ...
    total_card_balances: u128,            // Σ card.balance, for the solvency check
    pending_payouts: LookupMap<AccountId, u128>, // seller proceeds whose transfer failed
    total_pending_payouts: u128,
}

#[near(serializers = [borsh, json])]
pub struct Card {
    dna: u32,
    balance: u128,           // yoctoNEAR held for this token
    minted_at: u64,          // ns
    held_since: u64,         // ns, reset on every owner change
    trades: u32,             // completed built-in market sales
    royalties_earned: u128,  // lifetime royalty credits
    deposited_total: u128,   // lifetime top-ups
    withdrawn_total: u128,   // lifetime withdrawals
    list_price: Option<u128>,// Some(price) while listed on the built-in market
}
```

Constants, in one block at the top of `lib.rs`:

| Constant | Value | Meaning |
|---|---|---|
| `MINT_PRICE` | 1 NEAR | Primary sale. Sent to `creator`. |
| `STORAGE_RESERVE` | 0.02 NEAR | Kept by the contract at mint to cover this token's storage, with about 3× headroom (§5). |
| `ROYALTY_BPS` | 1000 (10%) | Share of every built-in-market sale credited to the card |
| `MIN_LIST_PRICE` | 0.1 NEAR | Ensures the royalty is never zero |
| `MAX_SUPPLY` | 1000 | |
| `TIER_THRESHOLDS` | 0.5 / 2 / 10 NEAR | See §2.3 |

## 4. Methods

### 4.1 Keepers-specific calls

| Method | Who | Deposit | Effect |
|---|---|---|---|
| `new(creator, base_uri: Option<String>)` | deployer, once | — | Init |
| `mint() -> Token` | anyone | ≥ `MINT_PRICE + STORAGE_RESERVE` | Mints the next id to the caller, with DNA, balance 0 and tier matte. Sends `MINT_PRICE` to `creator`, refunds the excess, emits `nft_mint`. |
| `deposit(token_id)` | anyone | > 0 | `balance += deposit`. Emits `card_deposit` and `card_tier` if the tier changed. |
| `withdraw(token_id, amount: Option<U128>)` | owner only | exactly 1 yocto | See §4.3. `None` means the full balance. Refused while the card is listed. |
| `list(token_id, price)` | owner only | exactly 1 yocto | `price ≥ MIN_LIST_PRICE`. Sets `list_price`. |
| `delist(token_id)` | owner only | exactly 1 yocto | Clears `list_price` |
| `buy(token_id, min_card_balance)` | anyone but the owner | exactly `list_price` | See §4.4 |
| `claim_payout()` | anyone with a pending payout | — | Retries a seller payout whose transfer failed |
| `on_withdraw(token_id, amount)` / `on_seller_paid(seller, amount)` | `#[private]` callbacks | — | Undo the bookkeeping if the transfer failed (§4.3, §4.4) |

### 4.2 Views

| View | Returns |
|---|---|
| `card(token_id) -> CardView` | `owner_id`, `balance`, `tier`, `tier_name`, `next_tier_at`, `trades`, `held_since`, `minted_at`, `royalties_earned`, `deposited_total`, `withdrawn_total`, `list_price`, `dna` |
| `cards(from_index, limit)`, `cards_for_owner(account_id, from_index, limit)` | `Vec<CardView>` |
| `listings(from_index, limit)` | Listed cards with their price |
| `is_holder(account_id) -> bool` | The access credential (§7) |
| `config()` | creator, the constants and thresholds |
| `stats()` | supply, `total_card_balances`, `total_pending_payouts`, `account_balance` (solvency, §6) |

### 4.3 Withdraw (owner only, safe transfer)
1. **Checks:** 1 yocto attached, caller is the current owner, not listed, `0 < amount ≤ balance`.
2. **Effects:** `balance -= amount`, `withdrawn_total += amount`, `total_card_balances -= amount`. Emit `card_withdraw` (and `card_tier` if it changed).
3. **Interaction:** `Promise::transfer(owner, amount)` then `.then(on_withdraw(token_id, amount))`.
4. **Callback:** if the transfer failed, re-credit the **card**, not the caller. Ownership may have changed in between, and the funds belong to the token. Emit `card_withdraw_refunded`.

Because state is updated before the promise, a second withdraw in the same block cannot spend the same balance twice.

### 4.4 Buy (royalty split)
1. **Checks:** listed, `attached == list_price`, buyer ≠ owner, `card.balance ≥ min_card_balance`. The last check protects the buyer from a last-second change. Withdrawals are already blocked while listed, so this is defence in depth.
2. **Split:** `royalty = price × ROYALTY_BPS / 10_000` and `proceeds = price − royalty`.
3. **Effects, all in the same call:**
   - credit the card: `balance += royalty`, `royalties_earned += royalty`, `trades += 1`;
   - clear `list_price` and reset `held_since`;
   - move the token with `tokens.internal_transfer(owner → buyer)`, which also clears approvals and emits the standard `nft_transfer` event;
   - emit `card_sold`, `card_royalty`, and `card_tier` if the tier changed.
4. **Interaction:** `Promise::transfer(seller, proceeds)` then `.then(on_seller_paid)`. If the transfer failed (for example, the seller deleted their account), the amount goes to `pending_payouts[seller]`. The sale itself is never reverted.

### 4.5 Standard methods (NEP-171 / 177 / 178 / 181)
These delegate to `near-contract-standards`:
- core: `nft_transfer`, `nft_transfer_call`, `nft_resolve_transfer`, `nft_token`
- approvals: `nft_approve`, `nft_revoke`, `nft_revoke_all`, `nft_is_approved`
- enumeration: `nft_total_supply`, `nft_tokens`, `nft_supply_for_owner`, `nft_tokens_for_owner`
- metadata: `nft_metadata`

The transfer methods are thin wrappers that also run `on_owner_change(token_id)`, which clears `list_price` and resets `held_since`. `nft_resolve_transfer` runs it again if the receiver returned the token. `nft_token` adds dynamic metadata: a title like "Keeper #12 · Holographic", the SVG `media`, and `extra` = a JSON `CardView`.

### 4.6 Deviations from the standards

These will also go in the README.

| Area | Deviation |
|---|---|
| **NEP-199 payouts** | Not implemented. Royalties are enforced only by the built-in market (§2.4). |
| **Dynamic metadata** | `nft_token` metadata changes with the tier. `media_hash` is omitted because the media is dynamic. |
| **`held_since` after a returned transfer** | If an `nft_transfer_call` receiver returns the token, the previous owner's `held_since` is reset to the return time. This value is informational only and is not used for the tier. |

## 5. Storage costs

At NEAR's 10¹⁹ yoctoNEAR per byte (1 NEAR per 100 KB):

| Item | Estimated bytes | Cost | Paid by |
|---|---|---|---|
| Token core (owner, TreeMap node) | ~150 | | |
| NEP-177 token metadata (title only, the rest is dynamic) | ~100 | | |
| Enumeration: the owner's set, created on first token | ~180 (first) / ~70 (next) | | |
| `Card` struct + key | ~120 | | |
| **Per mint, worst case** | **~550** | **~0.0055 NEAR** | minter, out of `STORAGE_RESERVE` (0.02) |
| Transfer to an account that owns no Keeper yet | ~180 | ~0.0018 NEAR | contract, out of the accumulated reserves |
| One approval (NEP-178) | ~80 | ~0.0008 NEAR | approver (deposit required by the standard) |
| Listing | 16 (Option grows inside `Card`) | negligible | covered by the reserve |
| Pending payout entry | ~80 | ~0.0008 NEAR | contract (rare) |

A unit test measures the real `env::storage_usage()` delta for a mint and asserts that it is ≤ 40% of `STORAGE_RESERVE`. The contract account keeps a base balance of about 5 NEAR for its own code (~250–350 KB of WASM, about 3 NEAR).

**Gas budget for the front end:**

| Call | Gas |
|---|---|
| `mint` | 30 Tgas |
| `buy` | 50 Tgas (transfer plus callback) |
| `withdraw` | 30 Tgas |
| everything else | 10–15 Tgas |

## 6. Invariant (solvency)

```
account_balance ≥ total_card_balances + total_pending_payouts + storage_cost(storage_usage)
```

Every method that moves NEAR updates the totals in the same receipt, and `stats()` exposes all the terms so anyone can check it. Tests assert it after every scenario.

## 7. Access credential (the `/vault` page)

1. The front end asks the connected wallet to sign a NEP-413 message (`signMessage` in near-connect). That proves the visitor controls the account.
2. It then reads `is_holder(account_id)` (or `nft_tokens_for_owner`) from chain.
3. The page shows its holder-only content and the visitor's card stats only if the account is a holder.

After a sale, the next check returns `false` for the seller, so access moves with the token.

**Known limit:** this gate runs in the browser, so content shipped in the JS bundle is not secret. Truly secret content would need a server that verifies the same NEP-413 signature and view. That is a stretch goal for Checkpoint E, using the existing testnet worker.

## 8. Threat model: how could a seller try to keep the money?

| # | Attack | Mitigation |
|---|---|---|
| 1 | Withdraw the card balance right before the buyer's `buy` lands | Withdraw is refused while listed. `buy` also requires `balance ≥ min_card_balance`, the amount the buyer saw. |
| 2 | Delist, withdraw, relist at the same price | The buyer's `min_card_balance` check fails, and the UI shows the new, lower balance before signing. |
| 3 | Keep an approval to pull the token back after the sale | `internal_transfer` clears every approval on each owner change. |
| 4 | Withdraw, let the transfer fail, then hope the refund lands in their wallet | The failed-transfer callback re-credits the **card**, never an account. |
| 5 | Two withdrawals racing in the same block | The balance is decremented before the promise is created (checks → effects → interactions). |
| 6 | Keep the royalty from the sale | The royalty is credited to the card inside `buy`, atomically with the ownership change. The seller only receives `price − royalty`. |
| 7 | Keep access to `/vault` | Access is evaluated per request from `is_holder`, so there is no session or role to keep. |
| 8 | Sell off-contract to skip the royalty | Possible, as with any NEAR NFT. Documented in Known limits. |
| 9 | Re-entrancy through `nft_transfer_call` while listed | The listing is cleared at the start of any transfer, and `buy` requires the token to be listed. |

## 9. Events (NEP-297)

- **Standard events:** `nep171` `nft_mint` and `nft_transfer`, emitted by near-contract-standards.
- **Custom events:** `{"standard":"keepers","version":"1.0.0","event":…}`.

| Event | Data |
|---|---|
| `card_deposit` | token_id, from, amount, balance |
| `card_withdraw` | token_id, owner_id, amount, balance |
| `card_withdraw_refunded` | token_id, amount, balance |
| `card_listed` / `card_delisted` | token_id, price |
| `card_sold` | token_id, seller, buyer, price, royalty, seller_proceeds |
| `card_royalty` | token_id, amount, balance |
| `card_tier` | token_id, from, to |
| `payout_pending` / `payout_claimed` | account_id, amount |

The per-card counters (`royalties_earned`, `deposited_total`, `withdrawn_total`, `trades`) give each card a history summary without an indexer. The events give the full history.
